# Immersive 3D rebuild of the DEMAze marketing site (v1 review)

The rebuild adds a WebGL/motion presentation layer on top of the existing TanStack Start SSR site without disturbing the proven foundation. A new capability module (`src/lib/motion.ts`) supplies SSR-safe reduced-motion and WebGL probes; an R3F hero scene, a lenis smooth-scroll provider, and four motion primitives (reveal, magnetic, marquee, custom cursor) are composed into the rebuilt shell and all ten routes. The one hard risk — `three`/`@react-three/*` crashing SSR — is handled by isolating every three import behind a single mount-gated `lazy()` dynamic import in `client-canvas.tsx`; content, forms, and the honest `site-data.ts` model are untouched. Watch for: (1) **package-lock.json is out of sync** and blocks all four CI checks until a maintainer regenerates it with network access — confirmed, and the single gating item for CI green; (2) a **brief lenis init-then-teardown on reduced-motion clients** because `useReducedMotion()` starts `false` — likely; (3) the `has-custom-cursor` body class toggled in JS has no CSS counterpart — confirmed dead code, harmless.

**Verdict**: NEEDS_CHANGES

## High-level view

SSR safety is the crux of the change and it holds up. `three`, `@react-three/fiber`, and `@react-three/drei` are statically imported in exactly one module (`hero-scene.tsx`), which is only ever reached through `React.lazy(() => import(...))` inside `client-canvas.tsx`, itself gated behind `useHasMounted()`. No route or shared layout pulls three at module scope, and `lenis` is confined to `smooth-scroll.tsx` behind a mount effect. The server always renders the static fallback.

The capability layer is the backbone: `prefersReducedMotion()` and `supportsWebGL()` return conservative `false` on the server, and the React hooks start `false` so the first client render matches server markup. This hydration-parity choice is deliberate, but it means reduced-motion users get a one-render window where the lenis provider initializes before the preference is read and then tears itself down.

The API surface is small and internal: no new env vars or endpoints. The CSP in `src/server.ts` widens by exactly two sources — `blob:` on `worker-src` (already present) and `blob:` added to `img-src` — both same-origin, justified in comments, with no `unsafe-eval`/`wasm` added. That is the minimal footprint the shipped procedural scene needs.

Accessibility and reduced-motion coverage are thorough: the canvas, cursor, and decorative layers are `aria-hidden`; the marquee ships a real pause `<button>` with `aria-pressed`/`aria-controls`; the custom cursor never hides the native cursor; and a CSS `[class*="immersive-"]` reduced-motion guard neutralizes the CSS-driven motion while JS gates disable lenis/R3F/magnetic/cursor. The honeypot-guarded Supabase forms and content invariants are preserved.

The gap that blocks shipping is operational, not architectural: `package-lock.json` contains none of the four new dependencies, so `npm ci` (and therefore every CI check) fails until it is regenerated. This cannot be fixed in the sandbox and must be done by a maintainer/CI step with network access before the branch can go green.

<summary>Details</summary>

### SSR isolation of the three layer

The whole design rests on one invariant: nothing rendered during SSR may statically import `three`. A grep of the tree confirms `three`/`@react-three/fiber`/`@react-three/drei` appear only in `hero-scene.tsx`, and `lenis` only in `smooth-scroll.tsx`. The path into three is:

```
route (index.tsx / site-shell.tsx)
   └─ ClientCanvas            (imports NO three; imports HeroScene via lazy())
        └─ lazy(() => import("@/components/three/hero-scene"))   ← only entry to three
             └─ hero-scene.tsx  (Canvas, useFrame, Float, THREE)
```

`ClientCanvas` renders the `fallback` unless `hasMounted && webglReady && !reducedMotion && inView`; both `hasMounted` and `webglReady` start `false`, so the lazy chunk is never requested on the server or the first client commit. The canvas carries `pointer-events: none` plus `aria-hidden`, so it neither steals clicks nor reaches assistive tech.

### Reduced-motion timing in the smooth-scroll provider

`SmoothScrollProvider` guards SSR (`typeof window === "undefined"`) and reduced motion, but the reduced-motion signal comes from `useReducedMotion()`, which initializes to `false` and only flips after its mount effect reads `matchMedia`. On the first commit the lenis-init effect sees `reducedMotion === false` and constructs a `Lenis` instance; when the preference resolves to `true`, the effect's dependency changes and the instance is destroyed. A reduced-motion user therefore gets a brief window with smooth scroll active before it is torn down.

`ClientCanvas` avoids the analogous flash because `canRenderCanvas` also requires `webglReady`, which starts `false` — the canvas can't mount on the first commit regardless of the reduced-motion value. The smooth-scroll path has no such second gate. Gating the lenis effect on `useHasMounted()` and reading `prefersReducedMotion()` synchronously at init time would close the window.

### CSP surface

`src/server.ts` widens the policy by the minimum the procedural scene needs: `img-src` gains `blob:` (canvas/WebGL readback and generated textures resolve as object URLs) alongside the existing `self`/`data:`; `worker-src 'self' blob:` was already present. No `unsafe-eval`, no `wasm-unsafe-eval`, no third-party host, and `connect-src` stays `'self'`. Since three core ships no WebAssembly and no draco/basis decoders are pulled in, the wasm sources were rightly omitted — but if a future feature adds a draco/basis loader, `wasm-unsafe-eval` will need adding.

### Accessibility and reduced-motion coverage

Coverage spans all six motion vectors: JS gates disable lenis, the R3F scene, `Magnetic` (only enabled on `(hover:hover) and (pointer:fine)` and `!prefersReducedMotion()`), and `CustomCursor` (same gate), while CSS neutralizes `.scroll-reveal` and every `[class*="immersive-"]` element via the `prefers-reduced-motion` guard. The custom cursor is `aria-hidden`, disabled on coarse/touch, and — verified — never sets `cursor: none`, so keyboard/AT hit-testing and focus visibility are unaffected.

Two loose ends: the `has-custom-cursor` body class is toggled but has no CSS rule, so it is dead code; and the marquee's pause button remains interactive under reduced motion even though the animation it controls is already frozen, making it a no-op control for those users.

### Foundation preservation

The Lovable Vite wrapper (`vite.config.ts`) is untouched — no bundled plugins re-added. Generated files (`images.ts`, `routeTree.gen.ts`) are not hand-edited. The Supabase contact/playbook forms keep the honeypot `website` field (`tabIndex -1`, aria-hidden) and hidden `startedAt`, and `forms.functions.ts`/`submission-guards.ts` are unchanged. `site-data.ts` is untouched, so `site-data.test.ts`'s invariants (services=4, projects>=16, metrics=4, technologies=8, industries>=15) still hold. Route head meta, `__root` JSON-LD/font-preloads/providers, and self-hosted fonts are preserved. Content sections now compose `Reveal`/`Magnetic`/`Marquee` but still source everything from `site-data.ts`, and headings stay ordered (`SectionHeading` → `<h2>`, cards → `<h3>`).

### Test quality

`motion.test.ts` (node env) asserts the server contract — with no `window`/`document`, `prefersReducedMotion()` and `supportsWebGL()` return `false` — and first asserts the DOM globals are absent so it can't pass for the wrong reason; it would fail if those guards were removed. Not covered: the client behavior of `useReducedMotion`/`useHasMounted`, `Magnetic`/`CustomCursor` pointer gating, and the ClientCanvas fallback matrix. The SSR build (the real proof the three layer doesn't crash server render) is only validated by CI, which cannot run here. Existing content and guard tests were not weakened.

### Lockfile / CI status

All four CI checks (typecheck, lint, test, build) are deferred to CI and cannot run in this INTEGRATIONS_ONLY sandbox — this is expected, not a code defect. The blocking consequence is concrete: `package-lock.json` contains none of `three`/`@react-three/fiber`/`@react-three/drei`/`lenis`/`@types/three`, so `npm ci` fails and no CI check can pass until the lockfile is regenerated by a maintainer/CI step with network access (`npm install`, then commit). Hand-editing the lockfile is correctly avoided. This is the single item gating a green pipeline and the reason for the NEEDS_CHANGES verdict.
